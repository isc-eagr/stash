# Scene Releases database upgrade

These SQL files are standalone fork upgrades. They are **not** part of Stash's upstream migration chain. The structural upgrades were applied to the main and Amt databases on 2026-09-23 after backups were taken; the planner-statistics upgrade was applied to both afterward. For another database, apply the structural upgrades only while Stash is stopped, after taking a verified backup. The activity and rating upgrades rebuild tables and must not be run twice. The planner-statistics upgrade is safe to rerun while Stash is running.

1. Identify the actual database file from the instance configuration. Make a SQLite-consistent backup (`sqlite3 <database> ".backup '<backup-file>'"`), then copy that backup to a separate rehearsal database. Keep its associated configuration and media files available; the SQL changes only the database.
2. If releases have never been installed, run `scene_releases.up.sql` on the rehearsal copy first. Then run `scene_releases_preflight.sql` before any v2 upgrade. Review dangling cover checksums, missing file rows, duplicate owners, primary flags, and `PRAGMA foreign_key_check`. Duplicate ownership and invalid primary flags need case-by-case repair; do not discard media or metadata to make counts pass. A missing cover checksum cannot be reconstructed without the original image bytes.
3. If releases already exist, do not rebuild that table; run `scene_releases_cover_guard.up.sql` for the legacy cover protection trigger. Run `scene_releases_metadata_v2.up.sql` for normalized metadata, histories, conversion request IDs, and the combined gallery view.
4. Run `scene_releases_activity_v2.up.sql` only after the base `scene_negative_markers` and `scene_multi_segment_loop_presets` tables exist. Run `scene_releases_rating_v2.up.sql` only after `rating_scores.up.sql` has installed the three advisor score tables. Both v2 files create guard tables before copying data, so a second run fails instead of replaying a destructive table rebuild.
5. Run `scene_releases_planner_stats.up.sql` to restore SQLite statistics for the rebuilt marker and rating tables. Then run `PRAGMA foreign_key_check;` and `scene_releases_preflight.sql` again. Verify the row counts for markers, negative markers, loop presets, and each rating-score table against the backup. Rehearse converting a populated scene to a release and back, including rating rows, cover bytes, marker links, O-counter timestamps, and primary files, on the copy only.
6. If the rehearsal passes, stop the live app, take another backup, apply the same sequence to the live database, and repeat the checks before restarting. If an upgrade fails, restore the whole database backup; do not attempt to reverse the table rebuild by hand.

The metadata upgrade uses `CREATE IF NOT EXISTS` and may be rerun if its first execution was interrupted. The activity and rating upgrades each use one transaction and their guard table is the reapplication check. Existing releases retain only metadata that was actually stored; missing historical cast, tags, ratings, or history cannot be inferred from the parent scene.

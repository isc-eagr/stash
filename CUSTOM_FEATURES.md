This document is the user-facing inventory of capabilities added on top of the official Stash **v0.31.0** release. It is intentionally organized by product feature, not by commit or implementation change. Refinements to an existing custom feature (for example, chart layout, query batching, or a new test) belong in that feature's notes and are not separate features here.

All custom code follows [`CUSTOM_CODE_CONVENTIONS.md`](CUSTOM_CODE_CONVENTIONS.md): standalone custom helpers and schema use the `_custom` suffix where applicable, schema extensions use `extend` blocks, and inline changes carry `CUSTOM` markers.

## 1. Marker performers and role-aware marker workflow

### Overview

Scene markers can be associated with performers in explicit **Top** (giving) and **Bottom** (receiving) roles. This replaces the old scene-level performer-tag workaround and makes marker-level participation queryable and editable. The same role model is used by scene details, performer cards, marker playback, partner views, and filters.

### User-visible behavior

- Marker create/edit forms provide separate Top and Bottom performer selectors with role-colored indicators (blue Top, green Bottom).
- All tag selectors, including New/Edit performer, scene, image, gallery, group, studio, and marker fields, keep the Create Tag option and require clicking it to create a tag. Enter still selects existing tags; Tab moves focus without selecting an option. The shared behavior lives in `ui/v2.5/src/components/Tags/TagSelect.tsx` and `tagSelectKeyboard_custom.ts`; `SceneMarkerForm.tsx` no longer needs per-field opt-ins. Focused coverage in `ui/v2.5/tests/tagSelectKeyboard_custom.test.ts` checks keyboard handling and shared selector wiring. No schema changes or new configuration dependencies; Settings > Interface's existing Disable Dropdown Create > Tag setting still controls whether the option appears.
- Scene marker cards, the chronological marker panel, marker playback, and marker viewers show the assigned performers and role.
- Performer details include a Markers tab containing only markers linked directly to that performer.
- The Partners tab groups co-performers by Sex, Oral, and Facial role, with shared timed-marker duration for Sex/Oral pairs and deduplicated partner portraits.
- Performer cards expose role scene counts and unique-partner counts. Lazy card statistics are loaded in one page-level request so the initial list fragment stays small.
- Role counts (Sex, Oral, Facial, Solo, Nut, Feet) render as boxed tiles: full tiles with labels under the Performer Detail image, compact tiles on performer cards, the scene card performer popover, and the Scene Detail Vato overview. Totals (Performer Detail, catalog and studio cards, Vato overview) move Sex, Oral, and Solo scene counts into the shared Scene Types bar (`Shared/SceneTypesBar_custom.tsx`, also used by studios) above Facial, Nut, and Feet tiles; every configured role shows, with zero tiles and zero legend items dimmed and unlinked, and compact bars drop legend percents. Scene-scoped strips keep their tiles and show only that scene's roles.
- Marker performer associations support full create/update/delete behavior through `top_performer_ids` and `bottom_performer_ids`. The deprecated `SceneMarker.performers` field, the legacy marker `performer_ids` input, `Performer.scene_marker_roles`, and `performerTagSceneCounts` were removed as unused.

### Storage and API

- `scene_marker_performers` stores `(scene_marker_id, performer_id, role)` with foreign keys and role indexes. The standalone SQL references are `scene_marker_performers.sql` and `scene_marker_performers_top_bottom.sql`.
- `SceneMarker.top_performers`, `SceneMarker.bottom_performers`, marker performer filters, performer role counts, partner counts, and `PerformerRoleStats` are exposed through custom GraphQL extensions.
- Role-aware scene-marker context queries use flattened tag ancestry and are batched by visible scene/marker IDs to avoid per-card queries.

### Key files

- `graphql/schema/types/scene-marker_custom.graphql`, `performer_custom.graphql`, and `filters_custom.graphql`
- `pkg/models/scene_marker.go`, `pkg/sqlite/scene_marker.go`, `pkg/sqlite/scene_marker_filter.go`
- `internal/api/resolver_model_scene_marker.go`, `resolver_model_performer.go`, and `resolver_query_find_performer_custom.go`
- `ui/v2.5/src/components/Scenes/SceneDetails/SceneMarkerForm.tsx`, `PrimaryTags.tsx`, and `SceneMarkerCard.tsx`
- `ui/v2.5/src/components/Performers/PerformerDetails/PerformerCategoryStrip.tsx`, `performerRoleTiles_custom.{ts,scss}`, `PerformerAppearsWithByRolePanel.tsx`, and `performerRoleStats_custom.ts`

### Tests

Focused coverage includes role CRUD, top/bottom count semantics, partner de-duplication, shared-duration merging, batched role statistics, and role-color consistency (`performer_partner_duration_custom_test.go`, `roleColors_custom.test.ts`, `performerRoleTiles_custom.test.ts`, and related performer tests).

## 2. Role-tag configuration and activity classification

### Overview

Settings > Custom provides configurable tag IDs for the role and event families used by the custom UI: Sex, Oral, Solo, Facial, Nut (the `orgasmTagId` setting), Feet, Really Hot, GOAT, 2nd Camera, and OStats exclusions. Descendant tags are resolved recursively wherever a family is used; primary and secondary marker tags are handled according to the feature consuming them.

UI copy calls the user's own orgasms (O Counter, O history, O Stats) **O** and performer orgasms (markers in the orgasm tag family) **Nut**. Code, GraphQL, config keys, and stored rating keys keep `orgasm` names; saved rating rows keep the label text that was current when they were rated.

### Behavior

- Sex, Oral, Solo, and Facial families drive marker classification, scene types, card icons, activity percentages, stats, and filters.
- Orgasm and Facial event counts are weighted once per assigned Top performer, with a minimum of one when a marker has no Top assignment.
- Really Hot and GOAT qualifiers can be descendants and can also arrive as secondary tags.
- A configured 2nd Camera family is excluded from orgasm/facial statistics and category strips, while remaining available to normal marker browsing and playback. The Scenes-page orgasm marker filter can also exclude it at marker level.
- Role colors and semantic categories are centralized in `roleColors_custom.ts` and shared by cards, filters, timelines, and stats.

### Key files

- `ui/v2.5/src/components/Settings/SettingsCustomPanel.tsx` and `SettingsInterfacePanel/SettingsInterfacePanel.tsx`
- `ui/v2.5/src/core/config.ts`
- `pkg/sqlite/role_tag_provider.go`, `pkg/scene/query_custom.go`, and `internal/api/resolver_custom.go`
- `graphql/schema/types/config_custom.graphql` and `filters_custom.graphql`

## 3. Advanced scene, marker, and performer filtering

### Overview

The fork adds marker-aware and role-aware criteria to the Scenes, Markers, Performers, Studios, Galleries, Images, and Groups catalogs. Filter editors serialize these criteria into GraphQL inputs; SQLite handlers perform the matching with recursive tag CTEs and `EXISTS` predicates.

### Marker and role criteria

- Scene Markers, Scene Markers: Exclude, and Marker Match (the Markers-page criterion, `marker_performers`) share one configuration model: tags (all required, optionally with sub-tags) plus vatos, each with an explicit role — Top, Bottom, Both (top and bottom on the same marker), or Any role. Named and unnamed vatos follow identical role rules. Groups saved with the old Either · OR toggle are migrated on load: a vato listed as both top and bottom becomes Any role, and everything else becomes AND. The GraphQL group input adds `either_performer_ids` and `either_unnamed_performers`; `performer_mode: "OR"` remains for internal drilldown links. The deprecated group fields `performer_countries`, `performer_ethnicities`, and `performer_rating`, and the never-applied `*_ethnicity_counts`/`*_country_counts` inputs, were removed.
- Explicit overlap groups require marker ranges to overlap. Directed tag inheritance is separate: an equal-or-longer source marker contributes tags only when its intersection covers at least 50% of the receiving marker. A wider marker never inherits from a narrower marker inside it.
- The Markers page has a Marker Match criterion, a Has Roles criterion (Top/Bottom checkboxes), a Studio criterion with hierarchical child-studio matching, and a unified include/exclude Performer Markers criterion.
- All marker configurations are built by one SQL builder, `pkg/sqlite/scene_marker_group_sql_custom.go`, used by the Scenes handler (`criterion_handlers_custom.go`) and the Markers handler (`scene_marker_filter_custom.go`). Every configuration must match a different marker. Each unnamed vato letter binds to one person, different letters bind to different people, and an unnamed vato is never one of the named vatos. Empty configurations are ignored. Marker Match with one configuration returns each matching marker unless a shorter overlapping marker matches the same tags and vatos; with several it returns the shortest of the overlapping matches. A single tag family skips redundant inheritance checks. Circular Oral reuses a bound, cycle-safe tag family (`scene_marker_filter_optimization_custom.go`), and Studio descendants use the studio `id` column. Tests: `scene_marker_filter_optimization_custom_test.go` (in-memory, including different-marker, distinct-vato, either-role, and shorter-marker cases), `scene_marker_configuration_custom_test.go` and `scene_marker_identity_custom_test.go` (integration), and the opt-in read-only `scene_marker_audit_custom_test.go`. See `docs/custom_marker_filter_audit_custom.md` for earlier measurements.
- Unnamed vatos (Vato A, Vato B, …) can be defined by ethnicity, country, rating, and Rating Advisor criteria. Reusing a letter requires the same actual person across the referenced roles/configurations.
- The shared editor (`MarkerFilterEditor.tsx`, `markerFilterEditor_custom.ts`, `markerFilterEditor_custom.scss`) numbers markers (Marker 1, 2, …) so they cannot be confused with vato letters, shows a plain-language summary (↑ top, ↓ bottom, ↑↓ both, no arrow for any role) in the modal, the filter summary, and the filter chip, and gives each unnamed vato a coloured letter badge. The Vatos section lists every vato in the marker with a role picker, edit, and remove; new vatos default to Any role, and a vato created from a marker is added to it. Apply drops empty markers and unused unnamed vatos and is disabled when nothing is left. Shared model helpers are in `ui/v2.5/src/models/list-filter/criteria/marker-group_custom.ts`; `markerFilterEditor_custom.test.ts` covers roles, legacy migration, summaries, pruning, draft isolation, rating criteria, and URL/saved-filter persistence. Cancel preserves the original filter.

### Scene and performer criteria

- Scene Type classifies Sex, Oral, Solo, and Facial scenes using configured tag families. Sex/Oral/Solo are mutually exclusive on Scenes; Facial is independently combinable. Performer selections use marker-level participation.
- Performer Markers filters (include and exclude) match marker participation, role, partner attributes, and tag ancestry. The unused `PerformerFilterType` inputs `marker_tags` (deprecated), `performer_marker_tags`, and `performer_marker_partners`, and the `partners.any_non_sex_bottomed/topped` metrics, were removed. Custom radio filters include Versatile Scenes, Circular Oral, Strict/Lenient Tops, and Strict/Lenient Bottoms.
- Performer country, ethnicity, rating, and profile-image-count criteria use database-backed values. Ethnicity searches (Vatos, Scenes, Markers, Galleries, Images, marker and unnamed-vato criteria) count Afrolatino as Black and Latino and Mixed as Black and White; stats and charts keep every ethnicity separate. An `__exact__` value (shown as Exact match) turns the expansion off for report drilldowns. Inclusive numeric operators (`>=`, `<=`) are available across numeric/date/duration controls.
- Custom criteria are highlighted in the filter picker so fork-only filters are easy to identify.
- Scene Activity/Quality percentage filters batch selected interval metrics over local candidates and preserve rounded comparisons, count queries, and nested logic. Scene Type and custom role filters use parameterized, cycle-safe tag-family sets; single-match Scene Marker groups stop early. Scene Performer Rating keeps ANY branches independent and enforces ALL for inclusive comparisons. See `docs/custom_scene_filter_audit_custom.md` for the audit and measured results. No schema, migration, or configuration changes.

### Key files

- `graphql/schema/types/filters_custom.graphql`, `pkg/models/filter.go`, and the `pkg/sqlite/*filter*_custom.go` handlers
- `ui/v2.5/src/models/list-filter/criteria/{scene-markers,marker-performers,performer-markers,unnamed-performer,scene-type,has-roles,custom-filters}_custom.ts`
- `ui/v2.5/src/components/List/Filters/{SceneMarkersFilter,SceneMarkersExcludeFilter,MarkerPerformersFilter,PerformerMarkersFilter,SceneTypeFilter,HasRolesFilter}.tsx`
- `ui/v2.5/src/models/list-filter/custom-filter-options_custom.ts` and `EditFilterDialog.tsx`

### Tests

SQLite and UI tests cover the 50% overlap boundary, exclusion behavior, role matching, unnamed-performer identity, tag ancestry, scene-type precedence, Has Roles combinations, profile-image counts, and custom-filter serialization. The scene-filter optimization tests additionally cover numeric operators, grouped/direct percentage aliases, AND/OR/NOT, counts/pagination/sorts, HAVING boundaries, cyclic ancestry, and performer-rating composition. The optional read-only filter audit compares original and optimized matching IDs.

## 4. Statistics dashboards

### Overview

The custom statistics experience is split into hidden, focused destinations instead of the retired `/customstats` page. Shared navigation links to `/scenestats`, `/vatostats`, `/ostats`, `/nutstats`, `/facialstats`, and the `/stats/playground` hub; Scene, Vato, O, Nut, and Facial Stats can also be embedded in Studio detail tabs with an optional child-studio scope.

### Shared date range and charts

- Every stats page has a **Dates** filter (All time, Last 30/90 days, Last 12 months, This year, Last year, Custom). It lives in the URL (`statsRange`, `statsFrom`, `statsTo`, `statsDateField`), survives refresh/back, and carries across the stats navigation links and O Stats drilldowns. Relative presets resolve to local calendar days.
- Scene, Vato, Nut, and Facial Stats can filter by **Release date** (effective date), **Date added**, or **O date**. O date keeps scenes with an O in the range and also limits O counts to that range. O Stats always filters by O date. The old "(past year)" podium options were removed in favor of the range.
- The date range narrows the shared `selected_scenes` scope, so studio scope, date range, totals, Activity & Ratings, Activity Matrix, Rating Advisor, and vato aggregates always agree. With a date range, Vato Stats lists only vatos with scenes in range.
- Every stats page renders the shared `StatsBarChart`: total and percent per bar, tooltips, "Sort by count" for ordered distributions, "Show all" for long charts, and Unknown badges. Charts where one item lands in several bars (ethnicity, country, roles, ages, marker tags, top vatos) mark the total with `*` and explain the overlap.
- Year charts show only years with a positive count, in chronological order. Month and day charts are zero-filled, so empty calendar periods show as zero bars. The year series live in `sceneStatsReleaseBuckets_custom.ts` and `oStatsDateSeries_custom.ts`; regression coverage in `statsBarChart_custom.test.ts` and `oStatsAggregates_custom.test.ts` includes gaps, explicit zero counts, empty data, and sorting. No schema or configuration changes.

### Stats page layout (all five stats pages)

- Every stats page follows one layout using the selected app theme (`--stats-*` tokens in `statsBarChart_custom.scss` read shared `--app-*` surfaces, accents, and radii). Big numbers sit in one row (`StatsKpiRow`), then the ranking, then charts in topic panels (the scene, the vatos, O's/nuts/facials, the action, ratings). Panels use a six-track grid: a row holds three small (`stats-small`), two medium (default), or one wide (`stats-wide`) chart, and each panel is ordered to fill whole rows; tablets pair small charts and stack medium ones, phones stack everything. The stats destination tiles, filter bar, chips, and O Stats timeline/calendar use the same tokens.
- Chart forms (`StatsCharts_custom.tsx` plus `StatsBarChart_custom.tsx`): columns for ordered values (the tallest column is highlighted, every tied column too unless all tie; columns can stack colored segments), ranked rows for categories with no order, split bars for parts of one whole (each segment and legend entry filters), two-sided bars for bottoms vs tops (bottoms left in the app's green, tops right in its blue; receivers are bottoms and givers tops), and a shaded giver × receiver grid. Country charts show tiny flags (`StatsCountryFlag`). Colors live in `utils/statsChartColors_custom.ts`; metallic tiers keep their metal colors and Regular / Really Hot / GOAT share one quality palette (neutral, gold, sapphire), with static glows for the latter two. The canonical palettes and meanings are documented in [UI_PALETTE_CUSTOM.md](docs/UI_PALETTE_CUSTOM.md).
- Rankings (`StatsTopCards_custom.tsx`) show five cards per row (scenes and vatos start with five and add ten) with rank-by chips, numbered covers or portraits with the value on the image, a muted detail line, Show N more, and a View as table toggle. All rankings persist Cards/Table in the URL: Scene and Vato Stats retain their existing `showList` key, while O/Nut/Facial Stats use shared `rankingView`. Refresh and Back restore the choice without losing other filters. Nut and Facial marker cards use the same chips and paging.
- Rating criteria on Scene Stats and Vato Stats are meters (`RatingAdvisorCriteriaMeters`): average points against each criterion's max, with set chips (Solo, Standard, Threesome, Group) and bonus/penalty counts, in a separate panel at the end of the page.
- Tests: `statsChartLayout_custom.test.ts`, `oStatsInteraction_custom.test.ts`, `vatoStatsSummary_custom.test.ts`, `markerEventStatsData_custom.test.ts` (quality stacks).

### Scene Stats (`/scenestats`)

- Only organized scenes count in the charts; Duration and Resolution count every scene (the compact query returns `organized`). Unorganized scenes have no markers yet, so Nuts and Facials Per Scene show them as an Unknown pill (it filters by Organized: No). Shares use scenes with a known value, including actual zero records. Missing values remain Unknown; the existing organized-scene scope keeps unassessed content separate.
- **Top Scenes** rank by O Count, Rating, Duration, File Size, Most Recent O, Vato Count, and Facial Count (five initially; Show more adds ten). O Count ties go to the scene that reached its count most recently. Each card shows the vato count and length.
- **The Scene**: release year/month/day (By Year/Month/Day chips), duration, and Rating full width, then Metallic Rating (including a set-but-unqualified `No Tier` bucket), Resolution (every scene, organized or not), and Scene Type. **The Vatos**: Vato Count (No Vatos 0, Solo 1, Standard 2, Threesome 3, Group 4+; only missing/invalid counts go to Unknown), Vato Ethnicity, and Vato Country. **O's, Nuts & Facials**: O Count, Nuts Per Scene, and Facials Per Scene.
- **Facials Per Scene** is one column per facial count (0 = None, which replaces Has Facial). Each column is stacked by the best facial in the scene: Regular, Really Hot, or GOAT (a facial marker with the GOAT tag; the backend now rolls GOAT tags into the compact marker groups). A column filters by facial count; a segment also filters by Best Facial. The separate Has Facial and Really Hot Facial Count charts are gone. **Nuts Per Scene** works the same way from the Nut Stats events (`markerEventStats(kind: ORGASM)`, so both pages count nuts alike), with Nuts and Best Nut filters.
- The KPI row holds average scene length, average scenes per vato, and Fucking / Mamando Rifle / Jerking Time with each one's share of activity time. Everything follows chart filters and the release drilldown; Activity & Ratings and Activity Matrix share the exact chart/release cohort, and filter chips stay visible in every section. Nut and facial totals live on Nut Stats and Facial Stats.
- Role families (Sex, Oral, Solo, Facial, Really Hot, GOAT) include every descendant tag: the backend rolls descendant marker tags up to the configured family tag.
- **Activity & Ratings** is a separate panel at the end of the overview (no longer a tab; old `?section=insights` links open the overview): Activity Type (Fucking, Mamando Rifle, Jerking) uses independent bars against the union of classified activity time; simultaneous categories may each reach 100%. Quality (Outstanding, Standard, Unclassified, Unusable) remains a partition, followed by the rating criteria meters; unclassified Other time is shown only as a raw duration in a scene's Stats tab. **Activity Matrix** stays its own tab. Both work globally and for Studio-scoped Scene Stats.
- Chart selections filter the page; URL-backed state restores Studio scope, filters, rank-by metric, table view, selected section, date range, and child-studio mode on refresh/back navigation.

### Vato Stats (`/vatostats`)

- Total Vatos and Meters of Pito lead the page, ahead of ranked vato portraits (titled "Best … pitos (By …)", five initially; Show more adds ten, with rank-by chips). **The Vatos**: Age at Scene (wide), Ethnicity, Country, Height, Verga, then Hair Color, Eye Color, and Circumcised. **Roles & Scenes**: **Scenes Per Vato** (wide) and the two role charts. **O's & Facials**: O Count and Facials Given/Received. **Ratings**: Rating (wide), Metallic Rating, and the vato rating criteria meters. **Scenes Per Vato** replaces the Total Scenes and four Sex/Oral Top/Bottom charts: chips switch between All (columns by scene-count range: 0, 1, 2, 3–5, 6–10, 11–20, 21+) and Sex or Oral (bottom scenes left, top scenes right per range); bars filter with `range:min-max` values. Only organized scenes count toward each vato's scene, role, O, facial, and age numbers (`organizedStatsSceneScopeCustom`; test `TestOrganizedStatsSceneScopeCustom`); vatos with no organized scenes still count in the Ethnicity, Hair Color, Eye Color, and Circumcised charts. Every total follows the selected vato cohort; criteria use the exact selected vatos, including zero-scene profiles and excluding unselected co-stars. The Meters of Pito tooltip shows measured/assumed counts with the 17 cm fallback (the card itself shows only the total). Unscoped Vato Stats includes zero-scene vatos so Total Scenes can show its zero bucket.
- O Count ties go to the vato who reached his count most recently (`most_recent_o_date` is a UTC timestamp for this). The ranked cards and the paged vato list share one ranking.
- **Age at Scene** counts distinct vatos who did at least one scene at each age; Unknown counts vatos with any scene whose age cannot be calculated.
- Solo-only and one-scene vatos are retained; unknown values appear as counters rather than zero-value bars.
- Role cards are replaced by clickable two-sided **By Role Strictness** (Pure and Lenient rows, bottoms left and tops right, Solo Only as a chip) and **By Role** (Sex/Oral/Facial rows, bottoms left and tops right, Solo as a chip) charts. Pure roles include sex and/or oral with no opposite sex/oral role; lenient roles require exclusively one sex role plus the opposite oral role. Facials do not affect strictness. Solo Only requires every scene in the current scope to be solo; Solo includes any solo appearance. Role bars count distinct vatos, retain zero counts, and follow the current scope and chart filters. Classification and drilldown predicates share `vatoStatsRoles_custom.ts`.

### O Stats (`/ostats`)

- **Latest** shows the five newest recorded O events in one row of five (timelines also run five per row) above the summary, with scene seek links, dates, ordinal chips, and associated marker tags. **View All** opens `/ostats/timeline`, a newest-first timeline with 25 events per page and Previous/Next links. Both preserve Dates and the studio tree; changing Dates resets the timeline to page one. Before this entry, full-library O history had no route; existing date/entity drilldowns remain available.
- Big numbers show Total O's, Most O's in a day, and Longest period without an O. Records use local calendar days (matching the date charts) and the dry spell runs to today or the end of the date range. The daily records and By Studio breakdown are global-only and omitted from the embedded Studio view.
- **O Calendar** is a GitHub-style heatmap for a chosen calendar year (Jan 1 to Dec 31) with total, active days, best day, and longest streak. Days before reliable tracking (2024-03-08) are hatched; each active day links to its timeline. The heatmap uses its own year, not the page date range.
- The By Year/Month/Day chart and the O Calendar follow the big numbers, then **The Scene** (By Scene Release Year and By Scene Rating full width, then By Metallic Tier beside By Studio, or full width on studio pages), **The Vatos** (By Performer Age full width, ethnicity, country), and **The Action** (activity type, marker tag).
- **Top Scenes** and **Top Vatos** follow the big numbers as large ranked image cards with O count and share. All stats rankings start with five cards; Show more adds ten. Each opens its O timeline. Ties go to whoever reached the count most recently. `sceneOCountsByScene`/`sceneOCountsByPerformer` return screenshot and portrait URLs. **By Scene Rating** and **By Metallic Tier** sum O's by the scene's rating bucket and metallic tier (including override tags and GOAT/bonus), with drilldowns at `/ostats/rating/:bucket` and `/ostats/tier/:tier`.
- Hidden O-date timelines and drilldowns by year/month/day, activity type, marker tag, vato ethnicity/country/age, Studio, and scene effective release year. Newest-first event timelines show associated marker tags, per-scene ordinal chips, scene/vato links, and optional exact O screenshots generated from video timestamps. Scene timelines show title, studio, and cast once above the events; each event retains its seek link. Mixed-scene timelines retain row identity. Reliable-date filtering starts at 2024-03-08 for date charts only.
- Every O Stats count, chart, ranking, and timeline includes release O's. A release O counts for its parent scene (rankings, ordinal chips, effective release year), its release's studio and cast, and the release markers it lands in; it links to the parent scene with that release selected, and its screenshot comes from the release file (`/scene-release/{id}/o/{oId}/screenshot`, generated by the O screenshot task). Scene Stats, Vato Stats, and the Rating Advisor O-count bonus count each scene's O's with its releases'. Event IDs of release O's are negated `scene_release_o_dates` rowids. Tests: `o_stats_release_custom_test.go`, `TestOScreenshotEventsQueryIncludesReleaseOCustom`.
- Studio details add O Stats beside Vato Stats (Nut and Facial Stats follow the same pattern). Every aggregate and drilldown filters to that studio, follows the Include child studios switch, and keeps the scope and date range while navigating.

### Nut Stats (`/nutstats`) and Facial Stats (`/facialstats`)

- Nut Stats covers performer orgasms (Orgasm tag family); Facial Stats covers the Facial family. One event is a marker counted once per assigned top (minimum one), skipping 2nd-camera markers, the same rule as the old Total Nuts/Total Facials cards, which moved here from Scene and Vato Stats. The top is the vato who came (giver); bottoms are receivers.
- A **Quality** column chart splits every nut or facial into Regular, Really Hot, and GOAT; a bar filters by quality.
- Big numbers: Total Nuts/Facials (“View markers” opens the marker list, narrowed to the matching scenes when filters or Dates apply), Total Nut/Facial Time (markers without an end count as 20 s), and on Nut Stats Estimated Liters (3 mL per nut).
- **Overview** lists the matching nut/facial markers as marker cards (screenshot first; the preview plays on hover, like the Markers page), twelve at a time with Show more. Only the visible cards are fetched (`findSceneMarkers(ids)`). **Sort by**: O Count (default; ties go to the most recent O), Latest O, Scene Rating, and Length; each card's badge shows the ranked value. A marker with two tops is one card.
- A second tab ranks **Top Nutters** (Nut Stats) or **Top Givers** and **Top Receivers** (Facial Stats); `section=top` keeps it in the URL. Shares are of the filtered events.
- Studio details have Nut Stats and Facial Stats tabs (`StudioMarkerEventStatsPanel.tsx`) scoped to the studio and its Include child studios switch.

## 5. Task Progress Tracker

### Overview

Tag-based task tracking records daily completions and incoming work for scenes, markers, images, galleries, performers, studios, and groups. Trackers support selectable scopes, active/paused/completed/archived lifecycle states, fixed batches, ordering, details/edit dialogs, and persisted history.

### Behavior

- Removing a direct tag or deleting a tagged item records completion; adding the tag records incoming work. Marker primary/secondary tag updates are atomic and deduplicated. Deleting a release also completes its deleted tagged markers for backlog and fixed-batch trackers; markers moved to another owner remain pending.
- Overall Progress tracks organized scenes. New scenes and organized-to-unorganized reversals are incoming work; unorganized-to-organized changes and deleting unorganized scenes are completions. Scene-to-release conversions and scene merges count through the same deletion path. Deleting an already-organized scene earns no duplicate completion. Completion history feeds daily/weekly/monthly goals, reports, activity charts, cumulative progress, and forecasts. Existing deletion snapshots automatically credit their drops in remaining work on the original reporting dates, including September 2026 onward wherever history exists; snapshots and current library counts are preserved, and deletions no longer appear as Removed scope. Cumulative totals and percentages follow each day's closing organized-scene snapshot, so they match the card (including scenes organized before tracking began), and period progress compares against the prior day's recorded close. Overall before/after percentages use those snapshots: deletions still earn goal credit but never count as organized scenes; deleting scenes can still change the percentage by changing the library total. Regular tracker deletions move pending items to completed while preserving completed-plus-remaining totals and fixed-batch goals.
- History uses America/Mexico_City dates. Details charts preserve zero-activity calendar days and use shared activity formats: a Monthly calendar and a Yearly contribution heatmap with monthly totals. Weekly graphs are removed from tracker, Overall Progress, and milestone Details. Calendar modes show the selected month/year with bounded Previous/Current/Next navigation and date, month, or year picking. Day clicks and keyboard activation open tracker activity from the activity charts; future days cannot be selected. A separate Totals trend tab retains cumulative/remaining lines, optional Incoming activity, baseline markers, 7d/30d/All history ranges, and its own bounded date selector. Completion-first hover popups retain lifetime percentages, daily percentage-point progress, effective goals, and incoming counts. Paginated daily activity and fixed-batch remaining-item links remain available. Scope changes (Added/Removed work) appear in hover popups, as daily-data columns when the range has any, and as blue/orange Totals trend markers; they do not count as completion progress or affect forecasts.
- Trackers automatically become Completed at 100%, including paused trackers and existing empty trackers at startup; new matching backlog work or restored fixed-batch members reactivates them. Completed rows use an Alpha Sapphire bar and glowing, shimmering percentage (static with reduced motion), show only the completed count, and omit finish planning. Today/This week/This month/This year remain through the last date containing recorded data, then disappear at the next Mexico City midnight, including in an open page. Goal per day, tag, mode, item types, and baseline resets are locked in the editor and API; title/description and archiving remain available. Completed Details retains completion totals, percentage, project/start context, and historical activity; it omits remaining summary metrics, forecasts, and pending links. Its cumulative history stops on the last recorded date; historical incoming/remaining counts remain available in the daily data table.
- Deleting a tracker’s tag keeps its tracker, event history, baseline members, daily goals, and milestone memberships. Completed trackers stay Completed; unfinished trackers become Archived with their last recorded remaining total, without inventing completion events. The original tag name is retained and Details shows Deleted tag instead of a broken link. Metadata remains editable; an archived tracker needs a replacement tag before it can resume or reset. Explicit tracker deletion still removes its dependent history.
- Paused trackers continue recording; archived trackers freeze activity and resume with a fresh baseline. Version checks reject stale edits, and restoring a deletion preserves baseline membership.
- The Trackers tab is a scoreboard. Overall Progress leads as a hero: a large percentage, large organized/to-go counts, a medal bar (earned progress as one rounded copper bar whose last segment, this week's net gain, is green, with the Bronze/Silver/Gold/Alpha Sapphire medals sitting on it at 25/50/75/100%), how many items the next medal needs, a daily-goal streak chip (consecutive goal days; an unfinished today never breaks it), a read-only Finish date chip, and Today/This week/This month/This year goal tiles with Goal met badges and the change against the previous period. Each tracker is one compact row: title, status, large done/left counts above the item types with Details, an Edit icon, and reorder arrows (Manual order) underneath, the current percentage, the same medal bar with the read-only Finish date and "N to next medal", and four period cells (completed/goal with a goal-colored meter, or raw totals in green without a goal). Medal tooltips show the first date reached or the items still needed. Status pills (with counts) replace the status dropdown; Sort adds Closest to next medal (items still needed, finished trackers last) and Estimated finish (soonest first from each tracker's saved plan, trackers without an estimate last, re-sorting as soon as a plan changes) beside Manual order and Progress high-to-low/low-to-high. Status and sort survive reloads through the URL; percentage and medal sorting preserve the saved manual order and hide reorder controls. The page uses the application theme's surfaces and copper accent. The finish planner lives only in tracker, milestone, and Overall Details: a card with the estimated date, a relative "in about…" line, a Current pace / My pace switch, the observed pace basis or a My pace items/day field, and an Assumes no new items arrive note. Rows, milestone rows, and the hero show that plan's date read-only (a copper checkered flag with a bold date; the hero shows it as a copper-tinted chip) and update live when it changes; manual rates and mode stay browser-local per entity under the same keys. Observed estimates require three complete days and exclude today's partial activity; positive net pace includes incoming work, otherwise a positive completion pace is explicitly labeled If no new items arrive. Paused/archived trackers show no automatic finish. Overall's daily goal remains database-backed and editable in Details, independently of the what-if planner.
- Newly earned checkpoints show achievement toasts at each 10% step for trackers and each 5% step for milestones, with tier awards at 25/50/75/100% for both, throughout the app, including when tags are removed or items are deleted from scenes, performers, galleries, and other catalogs. Achievements use the existing app toast component, height, header-only layout, and close control used after saving a scene. On desktop, achievements slide in from the left with the same half-second timing and edge spacing, while system notifications retain their right-side entrance. Mobile toasts retain their existing bottom-centered placement and slide. Persistent left/right containers prevent notifications from crossing the screen when errors interrupt achievements. Bronze/Silver/Gold/Alpha Sapphire add only their tier background colors at 25/50/75/100%; other steps use teal to distinguish achievements from ordinary green save events. Every toast shows the achieved percentage and tracker or milestone name beside a small metallic medal, or a trophy for Alpha Sapphire. The emblem reuses the checkpoint metal palette, with two soft glow and shimmer sweeps during the six-second toast; reduced-motion preferences keep it still. Each crossed step queues once, with a single tier toast at shared checkpoints; toasts auto-hide after six seconds and can be dismissed. Errors display before achievements, and achievements display before success messages. Errors interrupt achievements, which resume afterward; achievements interrupt successes, with the latest pending success shown after all achievements. Equal-priority achievements stay in arrival order; ordinary notifications retain their replacement behavior within their priority. The global watcher refreshes after successful relevant mutations, when the browser regains focus, and every minute while visible to catch other tabs or background work. Initial loads, existing historical checkpoints, new trackers, resets, and membership edits stay quiet; incoming work and repeated refreshes do not repeat earned badges within the session. Alpha Sapphire replaces Platinum at 100%. Overall Progress is excluded.
- Trackers and Overall Progress persist an optional Goal per day. Their cards and details show Today, This week, and This month completed/goal progress without repeating a work-progress percentage; trackers without a daily goal show the raw completed totals in green. Weekly periods start Monday, and current weekly/monthly targets count only elapsed calendar dates. Details history charts offer Monthly/Yearly views, defaulting to Monthly, and a separate Totals trend tab with 7-day, 30-day, or all-history ranges. Each view keeps its own selected date. Hover popups render on the page body, flipping and clamping to the viewport, so modals and scroll containers never clip them.
- Goal changes are effective on the current reporting date. Effective-dated goal history preserves prior daily colors and rolls old and new daily targets into their corresponding weekly/monthly periods instead of retroactively applying the latest goal.
- Unfinished tracker Details shows completed, remaining, and percentage summary cards above the shared history chart. Fixed-batch completed counts use the current baseline.
- The main progress page includes a browser-local Timer Countdown modal. A duration in minutes starts a real-time countdown with pause/resume and final stop controls. After reaching zero it tracks overtime from `00:00`; Stop freezes the timer and displays total active time taken, with no restart action available in that modal. The large display transitions from green through light green, yellow, orange, and red as the percentage remaining crosses 80%, 60%, 40%, and 20%.
- Milestones group trackers with an independent daily goal and optional target date. The Milestones tab is a ledger. A Growth over time chart draws every milestone's % complete on its first recorded day and then every two weeks (ending with the running week), or at each month's close once the history spans more than six months, starting where the data starts (one validated series color per milestone in list order, up to six; extras are noted; the swatch beside each milestone name matches its line). The vertical scale tops out at the first of 10/25/50/75/100% above the data so small percentages still read as growth, with neutral quarter gridlines, dashed Bronze/Silver/Gold lines inside the scale, a hover popup per point, medal dots on the day each was won, and date or month labels that skip crowded neighbors (every other label on phones). Milestone rows use the tracker scoreboard row: an expand arrow, swatch, name (opens Details), large done/left counts, tracker count and target status with required pace, the read-only Finish date, Details and an Edit icon under the counts, the previous close (muted) → current percentage on one line for the selected period, a 14px rounded medal bar whose green last segment is that period's net gain with the percentage gained and "N to next medal", and wider Day/Week/Month/Year cells (completions with a green ▲ or red ▼ change on one line and the previous count below). A Day/Week/Month/Year switch with Previous/Next/Current navigation (bounded by the first recorded activity) picks the period: it highlights that cell, re-anchors every row's cells and bar to the chosen day, week, month, or year, and sets the period of each row's tracker detail rows. Moved only (remembered per browser) hides milestones that completed nothing in that period. Details opens a per-milestone modal with totals, goal comparisons, the finish planner, item-type counts, Monthly/Yearly activity calendars, navigation, and Totals trend. Existing milestone URLs open that milestone in Details while all rows remain available; the selector and remembered selection were removed; the finish planner is browser-local per milestone. Overlapping items count once per tracker. Membership is dated: trackers picked when the milestone is created count their full history, a tracker added later brings its remaining items as Added work on that day, and a removed tracker's remaining items show as Removed while its completions recorded as a member stay in the milestone's totals and history. Removing and re-adding on the same day restores the original membership; adding and removing on the same day leaves no trace. Deleting a milestone leaves its trackers untouched.
- A period with no history before it opens at the first recorded day's opening close, so everything since tracking began (for example this year, with no prior-year data) counts as that period's gain and shows as 0.00% → current; work finished before tracking began stays in that opening close. ## 9. Multi-segment loops and marker playlists

### Multi-segment loops

The scene player supports unlimited A-B segments that play in order and repeat. Playback-rate-aware boundary timers and merged negative-marker ranges prevent early transitions and skip an entire overlapping undesirable range.

- **Player buttons:** the control bar has a loop toggle (one click on/off; with no segments it opens the editor) and an editor button whose badge counts saved presets.
- **Editor overlay:** the editor floats over the video inside the player, so it works in fullscreen, stays open while the controls hide, can be dragged (the position is kept while the page is open), and closes with Esc or ×. Keys typed in it do not reach the player hotkeys. It edits the current owner's loop. Segments can be added from the player, selected markers, or the scene Stats tab (Activity Type, Quality, and the Sex/Oral/Solo Quality boxes, which add that activity's Outstanding or Standard spans), then reordered by dragging a row's grip (or ArrowUp/ArrowDown on a focused grip), repeated alone, individually/bulk deleted, kept as a subset, and cleared. Clicking a row plays it and shows its ±1s and current-time controls. Timestamps seek like the Markers tab and show milliseconds when present.
- **Presets:** saved per scene or release, including segment titles, and shown as one-click chips; the chip matching the current segments is highlighted. Loading and clearing ask first only when the current segments match no saved preset. The save field is prefilled with the last loaded or saved preset, which can be re-saved without a prompt; overwriting a different preset or deleting one asks first.
- **Playback rules:** a seek into another segment plays that segment; a seek into a gap while playing returns to the current segment, while paused scrubbing is left alone. Deleting segments keeps the playing segment, turning the loop on keeps the segment under the playhead (or starts at the next one), and repeating one segment turns the loop on. Turning the loop off ends single-segment and remote-subset modes.
- **Temporary marker repeat:** the scrubber hover card has a compact Repeat Marker button (tooltip: Put this marker on repeat) beside Send Marker to Loop. It repeats that marker without changing the configured segments, enabled state, pending start, single-segment selection, or remote subset. Stop Repeating returns to the position captured on the first repeat click, where the existing loop resumes if enabled; otherwise regular playback continues. Switching repeated markers retains that original position. Paused playback stays paused. Markers without an end use the same 20-second fallback as Send Marker to Loop, capped at the video duration. Changing the video source clears the temporary repeat. No schema, migration, or configuration dependency.
- **Setting:** `configuration.ui.showMultiSegmentLoopControls` (default on) shows the player buttons. The multi-panel scene viewer uses the same buttons and opens the editor in a dialog.

### Marker playlist player

The Markers page can queue markers from multiple searches and open a sequential cross-scene player. The player double-buffers the next source, reuses the current source for markers on the same scene or release, shows generated marker screenshots, advances/replays/loops, exposes normal/fullscreen O recording and previous/next buttons, and keeps the active item visible by scrolling only the playlist. Rapid next/previous taps add up from the marker last asked for. Playlist rows reorder by dragging their grip (mouse, touch, or ArrowUp/ArrowDown on the grip) and the playing marker keeps playing through moves and removals; the URL follows each edit, so a reload or shared link keeps the edited playlist. A file that fails to load or play marks every marker that streams it, skips in the direction of travel with an in-player notice, and stops with a message when nothing is playable; clicking a marked row retries it. Loading a saved playlist navigates in place, and a lookup error (e.g. a deleted marker) shows the empty state. On phones the player stacks above the playlist at 16:9 (capped to the viewport height in landscape); fullscreen falls back to filling the viewport where element fullscreen is unavailable (iPhone Safari), rotates phones to landscape for landscape videos, and the first tap on hidden fullscreen controls only reveals them. Swiping left/right on the video plays the next/previous marker, performer chips are hidden on touch phones, and the screen stays awake while playing (Wake Lock needs HTTPS or localhost). Release markers stream their own file, attribute O events to their release, and open the parent scene with that release selected. Saved playlists persist marker IDs and order with a custom name and can be loaded or deleted later (playlists are not edited in place, so `findMarkerPlaylist` and `markerPlaylistUpdate` were removed).

### Scene Releases

A scene can contain alternate releases with independent metadata, Studio, cover, files, galleries, streams, and playback order. Releases inherit the parent scene's rating and Rating Advisor answers and never store their own; startup clears any left from before (`clearReleaseRatingsCustom`). Release-owned data includes cast, tags, groups, Stash IDs, custom fields, markers, negative ranges, loop presets, playback position, and play/O history. Release marker and skip-range editors write through owner-scoped mutations, and loop presets saved from the player belong to the selected release. A release with no file shows an empty media state instead of playing its parent. The playback context resets when its owner or primary file changes.

Conversions preserve source metadata and activity in one transaction, keep parent-scene data separate, and accept a persisted request ID for safe retries. The obsolete `transfer_o_history`/`transfer_markers` conversion flags were removed. File moves within a scene family preserve one primary file and prevent silent cross-family ownership. ## 21. StashDB Matches

Scenes carry **StashDB Matches**: how many users matched the scene on StashDB, computed as the sum of `submissions` across the scene's PHASH fingerprints. Every stash-box scene scrape (fingerprint lookup, text search, Tagger, Identify) already loads the scene's fingerprints; the query now also requests `submissions`. Only results from `stashdb.org` carry a count, so other stash-box instances never set or clear it. Unscraped scenes have no value, which is distinct from zero.

Removing or replacing a scene's StashDB ID resets its stored count to **0** through full updates, partial updates (including bulk/API edits), and database anonymisation. Unchanged StashDB links and changes to other stash-box IDs preserve the count. A save that removes all StashDB links cannot restore the previous count or clear it to null by including `stashdb_matches`; a fresh scrape with a new StashDB link can set a new count.

- **Scrape dialog:** a locked StashDB Matches row compares the stored and scraped counts; applying it saves with the scene. The Edit tab shows the count read-only.
- **Tagger:** each StashDB result shows its count with an include/exclude toggle, and Changes on Save lists the change.
- **Identify:** StashDB results refresh the count even when nothing else changes. Its field option defaults to Merge; Merge and Overwrite both refresh, and Ignore keeps the stored value.
- **Display, filter, and sort:** an optional scene table column, a number criterion (including is null/not null), and a sort where unscraped scenes stay last in both directions. Sorting by it shows the count on scene cards. The scene toolbar and scene cards (before Organized) show it with a fingerprint icon that opens the scene's StashDB fingerprints tab in a new tab.
- **Refresh task:** Settings → Tasks → **StashDB Matches → Refresh** re-checks every StashDB-linked scene, 25 per stash-box request (aliased `findScene` queries selecting fingerprint counts and `user_submitted`, within the endpoint's rate limit). It writes only counts that changed or were never fetched, skips scenes StashDB no longer has, keeps going past a failed request, and logs a changed/unchanged/not found/failed summary. **Report** (beside Refresh, opens in a new tab at `/stashdb-matches/report`) shows the latest run: totals and only changed scenes' before/after counts, grouped by studio and collapsed by default, biggest increases first within each studio. A separate **Not submitted by me** section lists successfully checked linked scenes with no PHASH marked `user_submitted` for the configured API-key account, including unchanged and zero-count scenes. Studios list: **Avg StashDB Matches** sort (studios without a value stay last in both directions) and a default-on table column. ## 22. Studio Site Sync

Studio pages for **Bilatinmen**, **NakedPapis**, and **LatinBoyz** (matched by studio name, ignoring case and spaces) show a **Sync from <site>** button beside Auto Tag. Its confirmation lists the four steps below as checkboxes, each with a one-line description and all checked by default (LatinBoyz has no pictures step), and queues one task that runs the chosen ones:

1. **Finds codes.** Bilatinmen reads `<code>-high` file names; NakedPapis reads `papi<code>` in file names or scene URLs and `<code>-high`/`-medium`/`-low` names (videos saved from a scene page, which the members index never links), then matches the rest by file name against the members `sexvideos`/`solovideos` index pages. New scenes get their members folder before the index links them, so names the index lacks are also matched against the video listings of the folders after its highest code (up to ten, stopping at two missing in a row). Copy suffixes such as ` (2)` and extensions are ignored, and joined copies of old multi-part scenes match their `<name>1`/`<name>part2` files when the code has at least two parts. Codes other scenes already hold (postponed ones included) are never assigned again. With this step off, only scenes that already have a code are touched. A name used by several codes is settled by an exact byte-size match (HEAD request); otherwise it is logged as ambiguous for a manual fix. LatinBoyz reads the digits after a file name's letter prefix (`HD2224`, `am245v2`, `wmv1069-3000HD`, `1700HD`) and can recover a missing code from the scene's public post. A public URL still fills metadata when neither the filename nor the page contains a code; a code is needed only to match local pictures. Unmatched filenames are listed in the report with instructions to add the public scene URL or enter Code.
2. **Fills metadata** for scenes with a new code or a missing title or date (with this step off, new codes are still saved): code, title, date, details, and site URLs. Only empty fields are written, so values set by hand are kept, and existing URLs are not repeated. Bilatinmen takes the title from its public preview page and the date from the members pictures listing; NakedPapis takes the date from the members video listing and the title/details from its `-high` scene page, plus the public page URL when it exists (`nude-latin-men/papi<code>/` or, for older scenes, directly under `nude-latin-men/`). Older scenes have no scene page, so their title comes from the name the members index shows above the scene's links; the site's `(part 2 of 2)` and `NO PICTURES` notes are dropped from names. LatinBoyz reads everything from its public WordPress post, found through the scene's own `latinboyz.com` URL or an exact code match against public image and trailer filenames (`am<code>`, `HD<code>`, `wmv<code>`). The paginated WordPress post index is read once per run, only when a code lookup is needed; incomplete indexes are never used. A missing or renamed saved page falls back to that index, and canonical URLs are added without repeating existing URLs. Multiple posts for a code and conflicting filename, stored, or public-page codes are reported without filling metadata or creating galleries. Older posts without a code need their public scene URL: the title from the heading, details from the post paragraphs without the members/join links and photo credits, and the date from the schema graph's `datePublished` (another JSON-LD block carries the last edit). Generic post titles are cut down to the model names ("Gay Latino Porn GABRIEL and CYCO" → "Gabriel & Cyco", "ROLO… Big thick Latin dicks" → "Rolo", "Cute Latino Twink – Brian" → "Brian"); a title that names nobody stays as the site wrote it. LatinBoyz also fills missing details or a missing public scene URL when the title and date already exist. Its post image replaces the generated cover when the sync fills an empty title, as the old script did.
3. **Downloads pictures** for scenes without a gallery whose `<pics folder>\model<code>` or `papi<code>` folder (Bilatinmen extras such as `extra142` use the code as the folder) does not exist yet or is empty (an older downloader left empty folders when a listing failed; an empty folder is replaced only once a new download finished). Files go to a `.part` staging folder renamed into place only when every image arrived, so an existing folder always means a finished download and an interrupted one resumes. LatinBoyz has no downloads: its picture sets are unzipped by hand into the pictures folder, and a folder belongs to the code in its last dash-separated part that is `am<code>` or a number of three or more digits (`latinboyz-model-brian-am2224`, `am1449`, `latinboyz-model-1455-tempo`), ignoring ` (1)` copy suffixes.
4. **Scans and builds galleries.** New folders, and existing non-empty ones Stash has no images for (never scanned, or scanned while still empty), are scanned with the default scan settings inside the same job; it then creates one gallery per coded scene without one, using the images in exactly that folder and its subfolders (zips extracted into a folder of their own name; never a name prefix, which let `papi99` pick up `papi990`). Several LatinBoyz folders with one code add each image once. The gallery copies the scene's title (or file name), code, date, details, studio, and URLs, links the scene, and gives the images the studio when they have none. Scenes without scanned pictures get no gallery, so a later run picks them up.

Scenes tagged `postpone` are skipped. Requests run one at a time with a short pause and reuse pages already read in the run. A members login the site refuses (or a missing one) stops further members requests: NakedPapis fails the task with a credentials message, while Bilatinmen keeps filling public titles, skips dates and pictures, and logs a warning saying so. LatinBoyz needs no login or subscription. Its Sync button tooltip explains the public URL fallback, when Code is needed, and the optional extracted-photo folder. Missing or unreadable LatinBoyz picture folders skip galleries with a report warning while public metadata continues; its members area (HTTP Basic auth on `members.latinboyz.com`) is never read. Progress shows on the button and in Settings → Tasks, and the log lists each ambiguous or already-claimed match plus run totals.

When the job ends, a **sync report** modal opens on the studio page: run totals, any error, cancellation, or members-login warning, a **Changed** table (scene, code, and badges for the fields filled, downloaded pictures, and a link to the new gallery), and a **Needs a look** table (not in the members index, ambiguous codes, a code already on another scene named in the message, not on the site, and read, cover, or download failures). Only the latest report per studio is kept, in memory until the next run or a restart; **Last report** beside the button reopens it, and a page opened while the job runs picks up its progress and report.

## 24. StashDB Changes

Settings → Tasks → **StashDB Changes** compares every StashDB-linked scene and vato with StashDB and lists what differs. **Check** queues one job for both; **Report** opens `/stashdb-changes` in a new tab. The report has Scenes and Vatos tabs, each with its own **Check** button that shows progress and reloads the report when the job ends. The report also follows a check queued elsewhere (Settings or another tab), found in the job queue by its description, so one Settings check fills both tabs even when the report opens mid-run. Checking writes nothing; only **Use StashDB** does.

- **Compared fields.** Scenes: title, studio code, date, studio, vatos, tags, details, director, and URLs. Vatos: name, disambiguation, aliases, gender, birthdate, death date, ethnicity, country, eye and hair color, height, measurements, breast type, career start/end, tattoos, piercings, and URLs. Images are not compared.
- **What counts.** Only values StashDB has: an empty StashDB field, a local-only URL or alias, and an unlinked local tag or vato never show. Whitespace, line endings, and (for enum-like vato fields) case are ignored; dates compare at StashDB's precision; URLs ignore scheme, `www.`, case, and a trailing slash; StashDB's `NA` breast type is not a value. Studios, vatos, and tags match by StashDB ID or by name/alias. List fields show **+** entries StashDB has that are missing locally and **−** local entries linked to StashDB that the StashDB scene dropped. Tags matching the scraper's excluded tag patterns are never suggested.
- **Gone from StashDB.** Entries StashDB deleted, merged (including StashDB redirects to another ID, which also compare fields), or no longer has are listed first, with links to the old and new StashDB pages.
- **Field picker.** A **Compare** checklist per tab hides fields from the report and stats without re-checking; each field shows how many entries differ on it. The choice is saved in the UI configuration. Changed scenes are grouped by studio (collapsed, rendered on open); vatos and gone entries page 100 at a time. Each entry is a card (blue edge for changed, orange for gone) with your value in red, StashDB's in green, list changes as green **+** / red **−** pills, and URLs shown without scheme or `www.`.
- **Apply.** Each field with something to take has **Use StashDB**; an entry with two or more has **Use all**, which applies only the fields the picker shows. Scalars take the StashDB value. URLs and aliases append the **+** entries. Studios, vatos, and tags resolve to local ones by StashDB ID (stored with the report since this change; older reports fall back to names), then name, then alias, using upstream's scrape matchers; an ambiguous vato name or no match is skipped, never created, and a warning toast names what was skipped. **−** entries are never removed. Writes go through the scene and performer update paths (cast-change advisor sync, performer name/alias validation, update hooks). The applied fields drop out of the stored entry and the Apollo cache, so the report updates without a re-check; skipped and **−** entries stay, and a changed entry with nothing left drops out.
- **Runs.** Each kind's run replaces only that kind's report. Requests batch 25 entries (aliased `findScene`/`findPerformer`) within the endpoint's rate limit; a failed request skips its batch and counts as failed. A stopped job saves what it checked, marks it partial, and leaves later kinds' reports alone. Entries deleted locally drop out of the report; anonymised databases drop the report.

Storage is the fork-owned `stashdb_changes_runs` (one row per kind) and `stashdb_changes_entries` (entity, StashDB ID, status, merged-into ID, and a JSON array of field differences with the StashDB IDs of the studio and added vatos/tags), created idempotently at startup and recorded in `stashdb_changes.up.sql`.

- Backend: `pkg/stashbox/stashdb_changes_custom.go` (shared aliased lookup, also used by StashDB Matches), `pkg/models/stashdb_changes_custom.go`, `pkg/sqlite/stashdb_changes_custom.go` with hooks in `pkg/sqlite/{database.go,anonymise.go}`, `internal/manager/{task_stashdb_changes_custom.go,stashdb_changes_compare_custom.go}`, and `internal/api/{resolver_stashdb_changes_custom.go,resolver_stashdb_changes_apply_custom.go}`.

## 25. Merge and maintenance guidance

When merging a newer upstream Stash release:

1. Treat upstream as the base and layer these capabilities on top.
2. Preserve inline `// CUSTOM` blocks and all `_custom` files; adapt them to upstream APIs rather than replacing upstream behavior.
3. After schema changes or conflict resolution, run `make generate` (Windows: `mingw32-make generate`).
4. Run the narrowest relevant checks: `go build ./cmd/stash`, targeted UI lint/Prettier, `npm.cmd run check` for TypeScript changes, and `git diff --check`. Use `go build ./...` or a full UI build only when the changed surface requires it.

### Intentionally not standalone entries

The following are implementation refinements or parts of the features above, so they are not presented as new features:

- presentation-only chart/layout changes;
- Task Progress finish estimates and Overall Progress presentation;
- Studio/catalog active-sort badges and batched list queries;
- marker/scene mutation performance work and test-suite validation;
- one-off control, label, and copy adjustments.
